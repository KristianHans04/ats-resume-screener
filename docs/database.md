# Database Schema

The CSAS Engine uses Cloudflare D1, a highly scalable, serverless SQL database system based on SQLite. This document explains the structure of the database and how data relates to one another.

## Core Tables

The system is built upon three primary data tables:

### 1. The `users` Table
This table stores the account information for every person using the platform.
- **id:** A unique numerical identifier for the user.
- **username & email:** Contact and display information.
- **password_hash:** For security, passwords are encrypted (hashed). The system never stores plain-text passwords.
- **role:** A strict categorization that must be either `RECRUITER` or `CANDIDATE`. This field dictates what the user is allowed to do across the entire platform.

### 2. The `jobs` Table
This table stores all the job postings created by recruiters.
- **id:** A unique identifier for the job.
- **title, company, description, requirements:** The core text data describing the role. This text is critical as it is fed directly into the AI engine for evaluation.
- **recruiter_id:** This is a "Foreign Key." It points directly to a specific user in the `users` table. This creates a relationship ensuring that only the recruiter who created a job can edit or view its applicants.

### 3. The `applications` Table
This is the most complex and important table in the system. It connects a Candidate, a Job, and the AI's evaluations together.
- **job_id & candidate_id:** Foreign keys linking to the specific job applied for, and the specific user applying.
- **status:** Tracks the current state of the application (e.g., `PARSING`, `AWAITING_INQUIRY`, `COMPLETED`, `SHORTLISTED`, `REJECTED`).
- **classification:** The initial bucket the AI placed the resume in (e.g., `STRONG`, `UNDEREXPLAINED`, `REJECTED_WRONG_ROLE`).
- **ai_score:** The final numerical score (0-100) assigned by the AI engine.
- **rejection_reason:** If rejected, a plain-text reason generated by the AI explaining why.
- **semantic_gaps:** A stored list of specific skills the candidate was missing.
- **generated_questions:** The exact, customized interview questions the AI created for the candidate.
- **answers:** The exact text the candidate submitted in response to the AI's questions.

## Data Relationships
Because this is a Relational Database, tables are inherently connected:
- A single `User` (Recruiter) can have many `Jobs`.
- A single `Job` can have many `Applications`.
- A single `Application` always belongs to exactly one `User` (Candidate) and exactly one `Job`.

By structuring the database this way, the backend can quickly perform complex lookups, such as: "Show me all applications for Job X, sorted by the highest AI Score, and fetch the usernames of the candidates who applied."
